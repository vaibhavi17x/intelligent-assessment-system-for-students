# Security Architecture Documentation

## Overview

This document defines the security architecture and practices for the Intelligent Assessment System. Security is considered from the ground up, with defense-in-depth principles applied throughout the application.

## Verified Implementation Status (2026-10-17)

This document contains both implemented controls and future requirements. The current backend implements bcrypt password hashing, JWT authentication, Zod validation on auth/profile/password requests, Helmet, one configured CORS origin, and a global limit of 100 API requests per 15 minutes. It does not implement server-side token revocation, refresh tokens, HttpOnly cookies, per-authentication rate limits, file upload routes, audit-event writes, live AI integration, or teacher/class assignment relationships. Treat future controls below as requirements, not deployed protections.

## Security Principles

1. **Defense in Depth**: Multiple layers of security controls
2. **Least Privilege**: Users and services have minimum required access
3. **Secure by Default**: Secure configurations unless explicitly overridden
4. **Fail Securely**: System fails to a secure state
5. **Input Validation**: All inputs are validated and sanitized
6. **Audit Trail**: All sensitive actions are logged

## Authentication

### Password Security
- **Hashing Algorithm**: bcrypt with cost factor of 10
- **Salt**: Automatically generated by bcrypt
- **Minimum Length**: 8 characters
- **Complexity**: Current policy requires uppercase, lowercase, and a number; special characters are not required
- **Storage**: Only hashed passwords stored in database

### JWT Token Management
- **Algorithm**: HS256 (HMAC with SHA-256)
- **Secret**: Minimum 32 characters, stored in environment variable
- **Expiration**: 7 days (configurable)
- **Payload**: Contains user ID, role, and expiration time
- **Storage**: Client-side in localStorage (to be enhanced with httpOnly cookies in production)

### Token Structure
```json
{
  "sub": "user_id",
  "role": "STUDENT",
  "iat": 1635724800,
  "exp": 1636329600
}
```

### Authentication Flow
1. User submits credentials
2. Server validates credentials
3. Server generates JWT token
4. Server returns token to client
5. Client includes token in Authorization header
6. Server validates token on each request

## Authorization

### Role-Based Access Control (RBAC)

#### Roles
- **STUDENT**: Can take assessments, submit assignments, view own results
- **TEACHER**: Can create assessments, review submissions, view class analytics
- **ADMIN**: Full system access, user management, system configuration

#### Permission Matrix

| Resource | STUDENT | TEACHER | ADMIN |
|----------|---------|---------|-------|
| Users | Own profile only | Student profiles | All users |
| Subjects | View | View & Manage | Full access |
| Topics | View | View & Manage | Full access |
| Questions | View | View & Manage | Full access |
| Assessments | Take (if published) | Create & Manage | Full access |
| Assignments | Submit | Create & Manage | Full access |
| Submissions | Own only | All submissions | All submissions |
| AI Evaluation | View own | View all | Full access |
| Reviews | View own | Create & Manage | Full access |
| Analytics | View own | View class | Full access |

### Authorization Middleware
```typescript
export const requireRole = (...roles: Role[]) => {
  return (req: Request, res: Response, next: NextFunction) => {
    const user = req.user; // Set by auth middleware
    if (!roles.includes(user.role)) {
      throw new AppError(
        ErrorType.AUTHORIZATION_ERROR,
        'Insufficient permissions',
        403
      );
    }
    next();
  };
};
```

### Resource-Level Authorization
- Students can only access their own submissions and results
- Teacher-to-class assignment checks are not implemented; the current user lookup allows teachers to read any student profile
- Admins have full access to all resources

## Input Validation

### Validation Strategy
- All inputs validated using Zod schemas
- Validation occurs before business logic
- Type safety enforced by TypeScript
- Length limits enforced at multiple levels

### Validation Layers
1. **Frontend**: React Hook Form + Zod
2. **API**: Zod schemas in route handlers
3. **Database**: Prisma schema constraints

### Example Validation
```typescript
const createUserSchema = z.object({
  email: z.string().email().max(255),
  password: z.string().min(8).max(128),
  firstName: z.string().min(1).max(100),
  lastName: z.string().min(1).max(100)
});
```

### SQL Injection Prevention
- Prisma ORM parameterizes all queries
- No raw SQL queries without explicit approval
- Input validation prevents malicious payloads

### XSS Prevention
- React automatically escapes JSX content
- Content sanitization for user-generated HTML
- CSP headers configured via Helmet

## File Security

### File Upload Validation
- **File Type**: Whitelist based on extension and MIME type
- **File Size**: Maximum 10MB (configurable)
- **File Content**: Magic number validation (to be implemented)
- **Virus Scanning**: To be implemented for production

### Allowed File Types
- `.pdf` - PDF documents
- `.doc` - Word documents (legacy)
- `.docx` - Word documents
- `.txt` - Plain text files

### File Storage Security
- Files stored outside web root
- Randomized file names (UUID-based)
- Organized by category (assignment_submission, model_answer, etc.)
- Access control via API, not direct file access

### File Access Control
- Download authorization checked per request
- Students can only download their own submissions
- Teachers can download submissions for their classes
- Admins have full access

### File Lifecycle
- Automatic cleanup of temporary files
- Retention policy to be defined
- Secure deletion when required

## API Security

### Rate Limiting
- **Default**: 100 requests per 15 minutes per IP
- **Auth Endpoints**: A stricter limit is recommended but not implemented
- **File Upload**: 10 uploads per hour per user
- **Configurable per route**

### CORS Configuration
- **Development**: Localhost only
- **Production**: Whitelist of allowed domains
- **Methods**: GET, POST, PUT, PATCH, DELETE, OPTIONS
- **Headers**: Content-Type, Authorization
- **Credentials**: Supported

### Security Headers (Helmet)
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `X-XSS-Protection: 1; mode=block`
- `Strict-Transport-Security` (HTTPS only)
- `Content-Security-Policy` (to be configured)

### Request Size Limits
- **JSON Body**: 10MB maximum
- **File Upload**: 10MB maximum
- **URL Parameters**: 2KB maximum

## Data Protection

### Sensitive Data
- **Passwords**: Never logged, always hashed
- **JWT Secrets**: Environment variables only
- **API Keys**: Environment variables only
- **Database Credentials**: Environment variables only
- **Student Submissions**: Protected by authorization
- **Teacher Model Answers**: Protected by authorization
- **AI Evaluation Results**: Protected by authorization

### Data Encryption
- **At Rest**: Database encryption (PostgreSQL feature)
- **In Transit**: TLS/SSL for all connections
- **Backups**: Encrypted backups (to be implemented)

### Data Minimization
- Only collect necessary data
- Anonymize analytics data where possible
- Regular review of data collection practices

## Audit Trail

### Audit Events
All auditable actions record:
- **Actor**: User ID who performed the action
- **Action**: Type of action (CREATE, UPDATE, DELETE, etc.)
- **Resource**: Type of resource affected
- **Resource ID**: ID of affected resource
- **Timestamp**: When the action occurred
- **Previous Value**: Before state (for updates)
- **New Value**: After state (for updates)
- **IP Address**: Client IP address
- **User Agent**: Client user agent

### Audit Actions
- CREATE: Resource creation
- UPDATE: Resource modification
- DELETE: Resource deletion
- LOGIN: User login
- LOGOUT: User logout
- SUBMIT: Assessment/assignment submission
- EVALUATE: AI evaluation performed
- REVIEW: Teacher review performed
- APPROVE: Teacher approval
- REJECT: Teacher rejection
- EXPORT: Data export
- IMPORT: Data import

### Audit Query
- Immutable audit records
- Tamper-evident (to be implemented with digital signatures)
- Queryable by actor, action, resource, time range
- Exportable for compliance

## Environment Security

### Environment Variables
- Never commit `.env` files
- Use `.env.example` as template
- Different configs for dev/test/production
- Secrets managed via environment variables or secret manager

### Development vs Production
- Development: Local filesystem, relaxed CORS
- Production: Cloud storage, strict CORS, HTTPS required
- Separate databases for each environment
- No shared credentials between environments

### Secret Management
- Development: Environment variables
- Production: Secret manager (AWS Secrets Manager, HashiCorp Vault, etc.)
- Regular rotation of secrets
- No secrets in code or logs
